개요

레이더 센서가 독거 어르신 등 취약계층의 심박·호흡·낙상·재실 여부를 비접촉으로 감지하는 서비스입니다. 입사 첫해 초기 시스템을 직접 구축했고, 2년 차부터 합류한 팀장·팀원과 함께 해외 POC로 확장했습니다. 실서비스라 가용성과 데이터 무결성을 가장 중요하게 다뤘습니다.

운영 구조

나라별로 서버를 나눈 이유

  • 보관 기간을 나라별로 관리: POC 단계라 나라마다 데이터를 소규모로 쓰고, 보관 기간을 따로 조절해야 했습니다.
  • 지연 최소화: 센서와 같은 나라의 서버가 데이터를 받아, 실시간 감지에 필요한 응답 지연을 줄였습니다.
  • 나라별 통계의 의미: 데이터를 나라별로 나눠 두고, 통계가 필요한 데이터만 온프레미스 대용량 DB로 모아 국가별로 비교·분석했습니다.

담당 업무

다국가 센서 데이터 수집

  • 나라별 AWS EC2 인스턴스에 Nginx 리버스 프록시와 API·수신 서버·DB 컨테이너 구성
  • Python 멀티스레드 소켓 서버로 여러 센서의 동시 연결과 데이터 수신 처리
  • 수집량이 많을 때 DB 저장이 밀리는 문제를, 수집 컨테이너 수를 가변적으로 늘리고 Nginx 로드밸런서로 분산해 해결
  • 사용자 정보에 국가 코드와 API 도메인을 함께 저장해, 관제 웹이 사용자별로 해당 나라 API를 호출
  • 통계용 데이터는 온프레미스 대용량 DB로 모아 국가별로 분석

백엔드

  • Spring Boot 백엔드 서버, Spring Batch로 API 호출과 데이터 백업
  • Java로 센서 데이터 수신과 FFT 알고리즘 구현
  • NestJS·TypeORM·PostgreSQL 관제 API, API 호출 로깅 공용 모듈

관제 API(NestJS · TypeORM · PostgreSQL)와 수신 서버를 만들며 내린 결정과 이유입니다.

주제결정이유 · 효과
쿼리 작성 방식단순 CRUD와 조건이 여러 개 붙는 동적 필터는 TypeORM QueryBuilder, join·서브쿼리가 들어가는 복잡한 조회는 raw query. raw query도 값은 문자열로 잇지 않고 파라미터로 바인딩복잡한 쿼리는 TypeORM으로 표현하기 어렵고, TypeORM에 익숙하지 않은 사람도 SQL만 보고 유지보수할 수 있게 함. 바인딩으로 SQL 인젝션 차단
트랜잭션 · 연관 삭제마스터 권한의 수정·삭제는 한 트랜잭션으로 묶고, 연관 데이터는 DB CASCADE 대신 코드에서 테이블 순서대로 삭제운영 중인 테이블 정의를 바꾸는 위험을 피하고, 어떤 테이블의 데이터가 지워지는지 코드에 드러나 후임자도 파악하기 쉬움. 중간에 실패하면 전체 롤백하고 실패한 단계를 로그로 남겨 원인을 바로 추적
계층 조회기관·위치 4단계 계층을 부모 코드 기준으로 설계하위 데이터를 부모 코드 하나로 한 번에 조회해, 항목마다 쿼리가 반복되는 N+1을 구조적으로 방지
입력 검증class-validator 기반 DTO로 타입과 허용 값만 받음잘못된 값과 쿼리 인젝션 시도를 API 입구에서 차단
시간 저장DB에는 UTC로 저장하고, 화면에서 사용자 국가의 시간대(한국은 UTC+9)로 변환나라마다 시간대가 달라도 저장값이 하나의 기준이라 국가 간 비교·통계가 어긋나지 않음
인증비밀번호는 bcrypt(salt 포함)로 해시 저장. 로그인 만료는 고객 요청으로 두지 않음보호 대상자를 계속 지켜봐야 하는 관제 화면이라 자동 로그아웃으로 알림을 놓치면 안 됨. 대신 로그인 시도·IP를 기록해 이상 접속을 확인
중복 수신센서코드와 수신 시각이 5초 이내로 겹치면 저장하지 않도록 INSERT 쿼리에 조건 추가센서 버그로 같은 데이터가 반복 송신돼도 한 번만 저장. 메모리가 아닌 DB 기준이라 수집 컨테이너가 여러 개여도 동작
통계 조회조직별 통계를 테이블에 저장해 두고, 없으면 집계 후 저장 · 있으면 바로 조회. 하루 한 번 첫 조회가 갱신조회마다 집계하던 통계 화면 렌더링이 2~3초에서 즉시로 단축. 최초 저장 시각을 비교해 중복 저장 방지
날짜 형식나라마다 다른 날짜 표기와 Unix time을 하나의 형식으로 바꾸는 공용 함수를 만든 뒤 API 형식을 통일국가별 화면·통계에서 날짜가 어긋나는 문제를 한 곳에서 처리, 국가별로 꼭 필요한 예외만 유지
다국가 라우팅첫 접속은 브라우저 언어·지역 코드로 언어팩 적용 → 로그인 시 미들웨어 API로 대상 국가 API 결정 → 이후 사용자 국가 코드를 쿠키에 저장사용자마다 해당 나라 서버로 요청을 보내고 국가별 시간대를 적용
보안 로깅로그인 시도 계정의 기관·국가 코드, 시도 횟수, 접근 페이지, 상태 코드와 실패 사유, 마지막 로그인 날짜·IP를 DB에 기록하는 공용 모듈계정 잠김·다른 곳 로그인 같은 문의를 로그로 바로 확인 (사례 4)
API 호출 정리그리드·그래프 페이지가 같은 API를 여러 번 부르던 것을 렌더링에 필요한 데이터를 한 번에 받도록 변경같은 값을 반복 조회하던 서버 요청을 줄임

사례 1

센서 2,000대 이상에서 터진 수집 병목을 TCP 단기 연결과 수집 서버 자동 증설로 해결

상황
국내 POC를 포함해 센서 2,000대 이상이 5초마다 데이터를 보내자 수집 서버 한 대가 모든 데이터를 받아야 했습니다.
증상
데이터 누락률 증가, DB 저장 지연, 수집 서버 응답 저하, 로그 누락, 센서 접속 시 연결이 오래 걸림
원인
DB 커넥션을 늘려도 해결되지 않았습니다. 수집 서버 하나가 센서 2,000대 이상의 TCP 연결을 계속 유지하고 센서마다 응답까지 보내느라, 데이터를 제때 받지 못하는 것이 근본 원인이었습니다.
해결
  • 센서 로직이 연결을 스스로 끊지 않아, 서버가 데이터를 받으면 바로 연결을 끊도록 예외 처리를 추가해 TCP 단기 연결로 전환
  • 센서에 보내던 응답 메시지를 없애 연결마다 드는 처리 부담을 줄임
  • 데이터 없이 연결만 붙잡는 센서는 10초 타임아웃으로 정리
  • 단기 연결로 바꾼 뒤에도 저장 후 연결을 끊고 포트를 돌려받는 속도가 데이터가 들어오는 속도를 따라가지 못해 포트가 부족해짐 → 수신 처리를 멀티스레드로 바꾸고 수집 컨테이너를 여러 개로 나눔
  • 묶어서 저장하는 bulk_insert도 구현해 비교했지만, 이상 감지가 늦어지지 않고 장애 시 모아둔 데이터를 잃지 않도록 건당 저장을 유지하고 처리량은 컨테이너 증설로 확보
  • 5초마다 새로 연결하므로 Nginx 로드밸런서가 요청마다 다른 수집 컨테이너로 고르게 분산할 수 있게 됨
  • 부하를 보고 내부 IP·포트를 하나씩 늘려 수집 컨테이너를 자동으로 추가, DB 커넥션도 함께 조정
결과
수신이 빨라지고 누락률이 줄었으며, 수집 서버 부하가 분산돼 안정적으로 운영됐습니다. 같은 구조를 가상 센서 5만 대(5초 주기, 초당 약 1만 건)로 검증했습니다. 송신기 한 대로는 초당 1만 건을 보낼 수 없어 송신 컨테이너를 여러 개 띄웠고, 8 vCPU·32GB EC2를 Spot으로 띄워 24시간·48시간 동안 실행했고, Spot 덕분에 테스트 비용을 82% 줄였습니다. DB에 저장된 결과를 5초 주기 기준으로 집계한 누락률은 1% 미만이었습니다.
지금이라면
자동 증설을 직접 만든 스크립트 대신 Kubernetes 자동 확장으로 옮기고, 수집과 DB 저장 사이에 메시지 큐를 두어 저장이 밀려도 수신이 막히지 않게 하겠습니다.

인프라 구성과 약정 방식을 비교해 EC2 비용 30% 절감을 제안·도입

상황

비교

  • RDS vs EC2 안의 DB 컨테이너: 인스턴스 하나에 API·수신 서버·DB를 묶으면 비용이 낮고 나라별로 한 번에 배포·관리할 수 있어 DB 컨테이너로 결정
  • 온디맨드 vs 1년 약정(Saving Plan): 장기 운영을 전제로 약정이 더 저렴

지금이라면
DB를 컨테이너로 운영하며 포기한 자동 백업·장애 전환을 비용과 함께 표로 비교해, 서비스가 커지는 시점에 RDS로 옮길 기준을 미리 정해 두겠습니다.

개요

실무에서 깊게 다루지 못한 이벤트 기반 아키텍처를 직접 설계하려고 만든 프로젝트입니다. 가상 결제 트래픽을 흘려 이상 징후를 자동으로 탐지하고, AI가 운영 리포트를 작성하며, 이 흐름을 실시간 대시보드로 보여줍니다.

화면

설계와 운영

설계

  • Java·Spring Boot 결제 API가 Kafka로 이벤트 발행, 컨슈머가 PostgreSQL(영속 기록)과 Redis(실시간 TPS·에러율)에 역할을 나눠 저장
  • Python으로 트래픽 생성·이상 탐지·Gemini 기반 AI 리포트, TypeScript로 게이트웨이·WebSocket 서버·React 대시보드
  • AI 리포트 에이전트가 MCP 서버를 도구로 호출해 Kafka Lag·지표·DB 데이터 조회

운영

  • k3s와 Terraform으로 AWS(Spot)·Oracle Cloud에 배포
  • Prometheus·Grafana·Tempo로 지표와 분산 트레이싱, 이상 알림은 n8n을 거쳐 Slack
  • k6로 단일 노드(t3.large) 안정 한계 약 65~70 TPS 측정(p95 500ms 기준), GitHub Actions CI
